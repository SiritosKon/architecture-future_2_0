# Task 1. Целевая архитектура и приоритизация проблем

## Целевая архитектура (C4, контейнеры)

![C4 Container — целевая архитектура «Будущее 2.0»](C4-container-target.drawio.png)

Исходник диаграммы: [`C4-container-target.drawio`](C4-container-target.drawio).

Текущая боль «Будущего 2.0» — монолитный DWH на SQL Server 2008, в который стянуты и данные всех направлений, и бизнес-логика. Любой новый бизнес или отчёт означает новые трансформации внутри DWH: растёт time-to-market, отчёты строятся часами, направления не могут развиваться независимо.

Целевое состояние строится по модели **Data Mesh на облачной платформе**: данными владеют домены, а не центральная команда DWH; платформа self-serve даёт доменам единый инструментарий, а бизнес-пользователь получает отчёты через **портал самообслуживания** в пределах своего уровня доступа.

Слои на диаграмме (снизу вверх — поток данных):

- **Источники** — операционные системы доменов (клиника, финтех на Go/Java, ИИ на Python, будущие партнёры). Бизнес-логика остаётся в сервисах доменов, а **не** в хранилище. Легаси-DWH сохраняется временно как операционная БД клиники и постепенно выводится (strangler fig).
- **Приём данных** — Kafka-стриминг доменных событий и CDC-коннекторы вместо старой шины ESB (Apache Camel). Входные контракты проверяют схему и качество.
- **Платформа данных (self-serve, облако)** — облачный Lakehouse (объектное хранилище + табличный формат), движок запросов (Trino/ClickHouse), семантический слой с метриками, каталог данных с lineage и оркестрация (dbt/Airflow).
- **Домены данных (Data Mesh)** — каждый домен публикует свои data products по контрактам. Новые домены (фарма, электроника) подключаются как ещё одна ячейка mesh без доработки ядра.
- **Потребление (self-service)** — портал самообслуживания с конструктором отчётов (MVP), BI-дашборды, Data API для выгрузок и интеграций.
- **Governance & Security (сквозной слой)** — IAM/SSO с уровнями доступа, федеративное управление (политики, data contracts), фильтр медданных (медкарты и исследования не попадают в аналитику), аудит доступа, отказоустойчивость (бэкап, гео-распределение).

### Как целевая архитектура поддерживает ключевые бизнес-сценарии

| # | Бизнес-сценарий | Чем обеспечивается на диаграмме |
|---|---|---|
| ① | **Быстрая подготовка отчётности** | Портал самообслуживания + семантический слой + Lakehouse/Query Engine. Отчёт собирается из готовых data products и метрик за минуты, без цепочки ручных трансформаций в DWH. |
| ② | **Независимое развитие финтех- и ИИ-направлений** | У каждого домена своя операционная система и свои data products. Команды релизят изменения независимо, не трогая общий DWH и не блокируя друг друга. |
| ③ | **Масштабирование под новые бизнесы** | Фарма и электроника подключаются как новые домены mesh через входные контракты и платформу self-serve — без переписывания ядра и без роста логики в хранилище. |
| ④ | **Качество медицинских и финансовых сервисов** | Фильтр медданных исключает медкарты/исследования из аналитики; IAM разграничивает доступ по уровням; аудит фиксирует обращения; отказоустойчивость и гео-распределение защищают критичные фин- и мед-сервисы. |

## Анализ проблемных мест

Проблемы текущего состояния с указанием затрагиваемых бизнес-сценариев и бизнес-последствий.

| # | Проблема | Затрагиваемый бизнес-сценарий | Бизнес-последствие |
|---|---|---|---|
| P1 | **Отчёты строятся часами.** Сотни ТБ в одном DWH, огромное число трансформаций на каждый отчёт | Подготовка управленческой и операционной отчётности | Задержки в принятии управленческих решений; аналитика не успевает за бизнесом |
| P2 | **Бизнес-логика «зашита» в DWH.** Логика финтеха и ИИ реализована поверх хранилища | Независимое развитие финтех- и ИИ-направлений | Любая доработка направления = изменение в общем DWH; команды блокируют друг друга, падает time-to-market |
| P3 | **Монолитное хранилище без границ доменов.** Все данные (клиенты, финансы, кредиты, HR, инвентаризация, медицина) в одной системе | Масштабирование под новые бизнесы (фарма, электроника) | Подключение нового направления требует вмешательства в ядро; стоимость и риск каждого расширения растут |
| P4 | **SQL Server 2008 — устаревшая и неподдерживаемая платформа.** EOL, не масштабируется горизонтально | Все сценарии работы с данными; надёжность сервисов | Технические и лицензионные риски, потолок производительности, уязвимости без патчей |
| P5 | **PowerBuilder-интерфейс операторов — легаси.** Узкий рынок специалистов, дорогая поддержка | Операционная работа клиник | Высокая стоимость сопровождения, риск остановки при уходе разработчиков |
| P6 | **Power BI с большим числом кастомизаций поверх DWH** | Подготовка отчётности, self-service аналитика | Отчёты хрупкие и трудно воспроизводимые; нельзя дать пользователям безопасное самообслуживание |
| P7 | **Старая шина ESB (Apache Camel) как единственный интеграционный слой** | Интеграция новых сервисов и партнёров | Жёсткая связность, сложно добавлять источники/потребители; интеграции — узкое место при росте |
| P8 | **Нет разграничения доступа по уровням и аудита на данных.** Доступ к чувствительным мед/фин-данным не управляется централизованно | Качество и безопасность мед/фин сервисов; комплаенс | Риск утечки медицинских и финансовых данных, штрафы регуляторов, потеря доверия |
| P9 | **Медицинские данные не отделены от аналитического контура.** Медкарты, истории болезней и исследования лежат в том же DWH | Витрина данных (по условию медданные в аналитику не включаются) | Риск попадания особо чувствительных данных в отчёты; нарушение требований к обработке медданных |
| P10 | **Нет каталога данных и data lineage.** Непонятно, где какие данные и откуда взялись | Самообслуживание, доверие к отчётности | Пользователи не находят нужные данные и не доверяют цифрам; дублирование витрин |
| P11 | **Отсутствие облачной отказоустойчивости.** Нет резервирования и гео-распределения для критичных систем | Надёжность финансовых и медицинских сервисов | Простои критичных сервисов → прямые финансовые и репутационные потери |

## Приоритизация проблем

Приоритизация выполнена двумя методами и увязана с целями бизнеса: выручка, time-to-market, качество мед/фин сервисов, масштабируемость, снижение затрат.

### Привязка к целям бизнеса

| Цель бизнеса | Какие проблемы мешают |
|---|---|
| Скорость принятия решений (быстрая отчётность) | P1, P6, P10 |
| Time-to-market и независимость направлений | P2, P3, P7 |
| Масштабирование под новые бизнесы | P3, P4, P7 |
| Качество и безопасность мед/фин сервисов, комплаенс | P8, P9, P11 |
| Снижение затрат и технических рисков | P4, P5 |

### MoSCoW

**Must have** (без этого цели года недостижимы)
- **P2 — логика в DWH.** Корень независимого развития; без выноса логики портал и доменная модель не заработают.
- **P1 — часовые отчёты.** Прямой удар по скорости решений; ради этого и затевается витрина данных.
- **P9 — медданные в аналитическом контуре.** Жёсткое требование условия и регуляторный риск.
- **P8 — разграничение доступа и аудит.** Без управления доступом портал к мед/фин данным открывать нельзя.
- **P3 — монолит без границ доменов.** База для масштабирования и для разделения на домены (Task 2).

**Should have** (сильно повышают ценность, но допускают поэтапность)
- **P7 — старая шина ESB.** Замена на стриминг/CDC критична, но вводится по доменам поэтапно.
- **P4 — SQL Server 2008.** Миграция обязательна, но допускает период сосуществования (strangler).
- **P11 — облачная отказоустойчивость.** Нужна для критичных сервисов; вводится по мере переезда в облако.

**Could have** (полезно, можно позже)
- **P6 — кастомизации Power BI.** Уходит с появлением семантического слоя и нового BI.
- **P10 — каталог и lineage.** Повышает доверие и самообслуживание; разворачивается после первых data products.

**Won't have** (в горизонте года не делаем)
- **P5 — замена PowerBuilder-интерфейса.** Операционный UI клиник можно оставить на период трансформации; по условию легаси в отдельных доменах временно допустимо.

### Матрица Эйзенхауэра

Оси: **Важность** (влияние на цели бизнеса) × **Срочность** (насколько блокирует ближайшие шаги трансформации).

| | Срочно | Не срочно |
|---|---|---|
| **Важно** | **Сделать сейчас:** P1, P2, P8, P9 | **Запланировать:** P3, P4, P7, P11 |
| **Не важно** | **Сделать попутно:** P6, P10 | **Отложить:** P5 |

### Вывод

Критичный путь трансформации: **вынести логику из DWH (P2) → задать границы доменов (P3) → поднять платформу и приём данных (P7) → закрыть доступ/аудит и изоляцию медданных (P8, P9) → дать быструю отчётность через портал (P1)**. Это напрямую работает на выручку (быстрые решения), time-to-market (независимые домены), качество сервисов (безопасность мед/фин данных) и масштабируемость (фарма и электроника). Декомпозиция по доменам и потоки данных — в Task 2, последовательность внедрения и ресурсы — в роадмапе Task 3.
