# Task 1. Целевая архитектура и приоритизация проблем

## Целевая архитектура (C4, контейнеры)

![C4 Container — целевая архитектура «Будущее 2.0»](C4-container-target.drawio.png)

Исходник диаграммы: [`C4-container-target.drawio`](C4-container-target.drawio).

Сейчас всё держится на монолитном DWH на SQL Server 2008. В нём лежат данные всех направлений и бизнес-логика. Поэтому любой новый отчёт или новый бизнес требует новых трансформаций внутри DWH. Из-за этого растёт time-to-market, отчёты строятся часами, а направления не могут развиваться независимо.

Целевое состояние через год — **Data Mesh на облачной платформе**. Данными владеют домены, а не центральная команда DWH. Общая платформа даёт доменам единый инструментарий. Бизнес-пользователь получает отчёты через **портал самообслуживания** в пределах своего уровня доступа.

### Контейнеры

| Контейнер | Технология | Роль |
|---|---|---|
| Портал самообслуживания | Web App | Витрина данных и конструктор отчётов для сотрудников доменов |
| BI и семантический слой | BI, metrics layer | Единые метрики и дашборды для руководства |
| Платформа данных | Облачный Lakehouse | Хранилище, движок запросов и каталог данных |
| Governance и доступ | IAM, data contracts | Уровни доступа, аудит, фильтр медданных |
| Шина событий | Kafka, CDC | Приём данных от доменов вместо старой ESB на Apache Camel |
| Сервисы клиник | Операционная система | Визиты, расписание, счета |
| ИИ-сервисы | Python | Модели для медицинских данных |
| Финтех-сервисы | Go, Java | Счета, кредиты, платежи |
| Домены партнёров | Будущие | Фарма и электроника, подключаются по той же схеме |
| Медицинские данные | Изолированное хранилище | Медкарты и исследования, доступны только ИИ-сервисам, в аналитику не попадают |
| Легаси DWH и PowerBuilder | SQL Server 2008 | Сохраняются временно, пока клиника не мигрирует; данные из них идут на платформу через CDC |

Бизнес-логика остаётся в сервисах доменов. В платформу попадают только данные, поэтому новая логика в хранилище больше не появляется.

### Как архитектура поддерживает бизнес-сценарии

На диаграмме контейнеры отмечены цветными метками сценариев.

| Бизнес-сценарий | Метка | Чем обеспечивается |
|---|---|---|
| Быстрая подготовка отчётности | отчётность | Портал, BI и семантический слой работают поверх облачного Lakehouse. Отчёт собирается из готовых data products за минуты, без цепочки трансформаций в DWH. |
| Независимое развитие финтех- и ИИ-направлений | независимость | У финтеха и ИИ свои сервисы. С платформой они связаны только через шину событий, поэтому команды релизятся независимо и не трогают общий DWH. |
| Масштабирование для новых бизнесов | масштаб | Домены партнёров подключаются к шине событий по тем же контрактам. Облачная платформа масштабируется под объём данных без переделки ядра. |
| Качество медицинских и финансовых сервисов | качество мед/фин | Медданные хранятся изолированно и не попадают в аналитику. Governance управляет уровнями доступа и аудитом. |

## Анализ проблемных мест

| Проблема | Затрагиваемый бизнес-сценарий | Бизнес-последствие |
|---|---|---|
| **Отчёты строятся часами.** Сотни ТБ в одном DWH, огромное число трансформаций на каждый отчёт | Подготовка управленческой и операционной отчётности | Задержки в принятии управленческих решений; аналитика не успевает за бизнесом |
| **Бизнес-логика «зашита» в DWH.** Логика финтеха и ИИ реализована поверх хранилища | Независимое развитие финтех- и ИИ-направлений | Любая доработка направления требует изменения общего DWH; команды блокируют друг друга, падает time-to-market |
| **Монолитное хранилище без границ доменов.** Все данные (клиенты, финансы, кредиты, HR, инвентаризация, медицина) в одной системе | Масштабирование для новых бизнесов (фарма, электроника) | Подключение нового направления требует вмешательства в ядро; стоимость и риск каждого расширения растут |
| **SQL Server 2008 устарел и не поддерживается.** EOL, не масштабируется горизонтально | Все сценарии работы с данными; надёжность сервисов | Технические и лицензионные риски, потолок производительности, уязвимости без патчей |
| **Интерфейс операторов на PowerBuilder.** Узкий рынок специалистов, дорогая поддержка | Операционная работа клиник | Высокая стоимость сопровождения, риск остановки при уходе разработчиков |
| **Power BI с большим числом кастомизаций поверх DWH** | Подготовка отчётности, самообслуживание | Отчёты хрупкие и трудно воспроизводимые; нельзя дать пользователям безопасное самообслуживание |
| **Старая шина ESB (Apache Camel) — единственный интеграционный слой** | Интеграция новых сервисов и партнёров | Жёсткая связность, сложно добавлять источники и потребителей; интеграции становятся узким местом при росте |
| **Нет разграничения доступа по уровням и аудита.** Доступ к мед- и фин-данным не управляется централизованно | Качество и безопасность мед/фин сервисов, комплаенс | Риск утечки медицинских и финансовых данных, штрафы регуляторов, потеря доверия |
| **Медицинские данные не отделены от аналитического контура.** Медкарты, истории болезней и исследования лежат в том же DWH | Витрина данных (по условию медданные в неё не входят) | Риск попадания особо чувствительных данных в отчёты; нарушение требований к обработке медданных |
| **Нет каталога данных и data lineage** | Самообслуживание, доверие к отчётности | Пользователи не находят нужные данные и не доверяют цифрам; витрины дублируются |
| **Нет облачной отказоустойчивости.** Нет резервирования и гео-распределения для критичных систем | Надёжность финансовых и медицинских сервисов | Простои критичных сервисов ведут к прямым финансовым и репутационным потерям |

## Приоритизация проблем

Проблемы приоритизированы двумя методами: MoSCoW и матрицей Эйзенхауэра. Обе привязаны к целям бизнеса: выручка, time-to-market, качество мед/фин сервисов, масштабируемость, снижение затрат.

### Привязка к целям бизнеса

| Цель бизнеса | Какие проблемы мешают |
|---|---|
| Скорость принятия решений | Отчёты строятся часами; кастомизации Power BI; нет каталога и lineage |
| Time-to-market и независимость направлений | Логика в DWH; монолит без границ доменов; старая ESB |
| Масштабирование для новых бизнесов | Монолит без границ доменов; SQL Server 2008; старая ESB |
| Качество и безопасность мед/фин сервисов, комплаенс | Нет разграничения доступа и аудита; медданные в аналитике; нет отказоустойчивости |
| Снижение затрат и технических рисков | SQL Server 2008; интерфейс на PowerBuilder |

### MoSCoW

| Категория | Проблема | Почему так |
|---|---|---|
| **Must have** | Логика в DWH | Корень проблемы: пока логика в DWH, домены не могут развиваться независимо, и портал не заработает |
| **Must have** | Отчёты строятся часами | Напрямую тормозит управленческие решения; витрину данных затевают именно ради этого |
| **Must have** | Медданные в аналитическом контуре | Жёсткое требование задания и регуляторный риск |
| **Must have** | Нет разграничения доступа и аудита | Без управления доступом портал к мед/фин данным открывать нельзя |
| **Must have** | Монолит без границ доменов | Без границ доменов не получится ни масштабироваться, ни разделить систему (Task 2) |
| **Should have** | Старая ESB | Заменить на стриминг/CDC критично, но это можно делать поэтапно по доменам |
| **Should have** | SQL Server 2008 | Мигрировать нужно, но допустим период сосуществования (strangler) |
| **Should have** | Нет облачной отказоустойчивости | Нужна критичным сервисам, вводится по мере переезда в облако |
| **Could have** | Кастомизации Power BI | Уходят сами, когда появятся семантический слой и новый BI |
| **Could have** | Нет каталога и lineage | Повышает доверие и самообслуживание, но разворачивается после первых data products |
| **Won't have** | Интерфейс на PowerBuilder | UI операторов можно оставить на время трансформации; по условию легаси в отдельных доменах временно допустимо |

### Матрица Эйзенхауэра

Оси: **важность** (влияние на цели бизнеса) × **срочность** (насколько проблема блокирует ближайшие шаги трансформации).

| | Срочно | Не срочно |
|---|---|---|
| **Важно** | **Сделать сейчас:** логика в DWH; отчёты строятся часами; нет разграничения доступа и аудита; медданные в аналитике | **Запланировать:** монолит без границ доменов; SQL Server 2008; старая ESB; нет отказоустойчивости |
| **Не важно** | **Сделать попутно:** кастомизации Power BI; нет каталога и lineage | **Отложить:** интерфейс на PowerBuilder |

### Вывод

Критичный путь трансформации:

1. вынести логику из DWH;
2. задать границы доменов;
3. поднять платформу и шину событий;
4. закрыть разграничение доступа и изолировать медданные;
5. дать быструю отчётность через портал.

Такой порядок работает на скорость решений, time-to-market за счёт независимых доменов, качество мед/фин сервисов и масштабирование под фарму и электронику. Декомпозиция по доменам — в Task 2, последовательность внедрения и ресурсы — в роадмапе Task 3.
