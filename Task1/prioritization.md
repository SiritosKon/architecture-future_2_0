# Приоритизация проблем

Приоритизация выполнена двумя методами и увязана с целями бизнеса: выручка, time-to-market, качество мед/фин сервисов, масштабируемость, снижение затрат.

## Привязка к целям бизнеса

| Цель бизнеса | Какие проблемы мешают |
|---|---|
| Скорость принятия решений (быстрая отчётность) | P1, P6, P10 |
| Time-to-market и независимость направлений | P2, P3, P7 |
| Масштабирование под новые бизнесы | P3, P4, P7 |
| Качество и безопасность мед/фин сервисов, комплаенс | P8, P9, P11 |
| Снижение затрат и технических рисков | P4, P5 |

## MoSCoW

### Must have (без этого цели года недостижимы)
- **P2 — логика в DWH.** Корень проблемы независимого развития; без выноса логики из DWH портал самообслуживания и доменная модель не заработают.
- **P1 — часовые отчёты.** Прямой удар по скорости решений; ради этого и затевается витрина данных.
- **P9 — медданные в аналитическом контуре.** Жёсткое требование условия (медданные в витрину не включаются) и регуляторный риск.
- **P8 — разграничение доступа и аудит.** Без управления доступом портал самообслуживания к мед/фин данным открывать нельзя.
- **P3 — монолит без границ доменов.** База для масштабирования и для разделения на домены (Task 2).

### Should have (сильно повышают ценность, но допускают поэтапность)
- **P7 — старая шина ESB.** Замена на стриминг/CDC критична для интеграций, но может вводиться по доменам поэтапно.
- **P4 — SQL Server 2008.** Миграция обязательна, но допускает период сосуществования (strangler): легаси временно живёт как операционная БД клиники.
- **P11 — облачная отказоустойчивость.** Нужна для критичных сервисов; вводится по мере переезда в облако.

### Could have (полезно, можно позже)
- **P6 — кастомизации Power BI.** Уходит естественно с появлением семантического слоя и нового BI.
- **P10 — каталог и lineage.** Повышает доверие и самообслуживание; разворачивается после появления первых data products.

### Won't have (в горизонте года не делаем)
- **P5 — замена PowerBuilder-интерфейса.** Операционный UI клиник можно оставить на период трансформации; по условию легаси в отдельных доменах временно допустимо. Переписывание UI не блокирует цели года.

## Матрица Эйзенхауэра

Оси: **Важность** (влияние на цели бизнеса) × **Срочность** (насколько блокирует ближайшие шаги трансформации).

| | Срочно | Не срочно |
|---|---|---|
| **Важно** | **Сделать сейчас:** P1 (часовые отчёты), P2 (логика в DWH), P8 (доступ/аудит), P9 (медданные вне аналитики) | **Запланировать:** P3 (границы доменов), P4 (SQL Server 2008), P7 (замена ESB), P11 (отказоустойчивость) |
| **Не важно** | **Делегировать / сделать попутно:** P6 (кастомизации Power BI), P10 (каталог и lineage) | **Отложить:** P5 (замена PowerBuilder-интерфейса) |

## Вывод

Критичный путь трансформации: **вынести логику из DWH (P2) → задать границы доменов (P3) → поднять платформу и приём данных (P7) → закрыть доступ/аудит и изоляцию медданных (P8, P9) → дать быструю отчётность через портал (P1)**. Это напрямую работает на выручку (быстрые решения), time-to-market (независимые домены), качество сервисов (безопасность мед/фин данных) и масштабируемость (подключение фармы и электроники). Декомпозиция по доменам и потоки данных — в Task 2, последовательность внедрения и ресурсы — в роадмапе Task 3.
