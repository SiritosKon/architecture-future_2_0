## Принцип разделения

Главное требование — **развивать направления независимо и не добавлять новую бизнес-логику в DWH**. Поэтому система режется по **бизнес-доменам (DDD / Data Mesh)**, а не по техническим слоям. Каждый домен:

- владеет своими операционными данными и сам отвечает за их качество;
- публикует наружу **data products по контрактам** (схема, SLA, семантика), а не даёт прямой доступ к своей БД;
- релизится независимо; изменения внутри домена не затрагивают ни другие домены, ни общее хранилище.

Платформа данных и governance вынесены в **enabling-домены** (переиспользуемый инструментарий и единые правила), а медицинские данные — в **изолированный контур**, который по условию не участвует в аналитике.

## Домены

| # | Домен | Тип (DDD) | Зона ответственности | Поддерживаемый бизнес-сценарий |
|---|---|---|---|---|
| 1 | **Клиника** | Core | Визиты, расписание, счета за услуги, операционная работа клиник | Операционная деятельность клиник, выручка за услуги |
| 2 | **Финтех / Банк** | Core | Счета, кредиты, платежи (банковская лицензия) | Независимое развитие финтех-направления |
| 3 | **ИИ-сервисы** | Core | ML-модели для медицинских данных | Независимое развитие ИИ-направления |
| 4 | **Медкарты и исследования** | Core (изолированный) | Истории болезни, диагностика, результаты исследований | Качество лечения; данные **вне аналитики** по требованию бизнеса и регуляторов |
| 5 | **Клиент / MDM** | Supporting | Единый профиль клиента (пациент = клиент банка) | Сквозная аналитика по клиенту без дублирования |
| 6 | **Корпоративные функции** | Supporting | HR/персонал, инвентаризация, финансовая отчётность | Управленческая отчётность головного офиса |
| 7–8 | **Платформа данных** (приём + lakehouse/семантика) | Enabling | Self-serve инструментарий: Kafka/CDC, Lakehouse, Query Engine, семантический слой, каталог | Быстрая отчётность; единый способ подключения новых доменов |
| 9 | **Витрина данных** | Consumer | Портал самообслуживания, конструктор отчётов, BI | Самообслуживание в рамках уровня доступа |
| — | **Governance & Security** | Enabling (сквозной) | IAM/доступ, data contracts, аудит | Безопасность и комплаенс мед/фин данных |
| + | **Домен партнёра** (фарма, электроника) | Core (future) | Данные будущих партнёров | Масштабирование на новые бизнесы |

## Потоки данных (по DFD)

1. **Операционные данные → платформа.** Домены 1, 2, 6 и будущие партнёры публикуют доменные события (Kafka) и отдают изменения через CDC в процесс «Приём данных». Входные контракты проверяют схему и качество. Бизнес-логика остаётся в доменах — в платформу идут только данные.
2. **ИИ-направление.** Медкарты (домен 4) передаются в ИИ-сервисы **внутри изолированного контура**; наружу в платформу ИИ отдаёт только **обезличенные метрики и признаки моделей**, без исходных медданных.
3. **Изоляция медданных.** Медкарты и исследования хранятся в отдельном хранилище (D2) и **не поступают** ни в lakehouse, ни в витрину — это прямо отмечено на диаграмме запрещающим потоком.
4. **Единый клиент.** Домен MDM раздаёт единый `клиентский ID` в клинику и финтех, что позволяет строить сквозную аналитику «пациент ↔ клиент банка» без слияния баз.
5. **Платформа → витрина.** Платформа материализует data products в Lakehouse (D1), регистрирует их в каталоге (D3) и отдаёт готовые витрины и метрики в портал самообслуживания.
6. **Потребление.** Операторы, команды доменов и головной офис получают отчёты из витрины — каждый в пределах своего уровня доступа.
7. **Governance.** IAM задаёт уровни доступа, data contracts — правила публикации, аудит фиксирует обращения; требования регуляторов входят через governance.

## Преимущества для бизнеса

- **Ускорение вывода продуктов (time-to-market).** Команды релизят свои домены независимо, без согласования изменений в общем DWH и без очереди к центральной команде.
- **Снижение зависимости от DWH.** Логика и данные живут в доменах; хранилище перестаёт быть узким местом и единой точкой отказа. Легаси-DWH выводится по частям (strangler), не блокируя развитие.
- **Масштабирование на новые бизнесы.** Фарма и электроника подключаются как ещё один домен через стандартные контракты и общую платформу — без переписывания ядра; стоимость и срок подключения предсказуемы.
- **Быстрая и надёжная отчётность.** Готовые data products и семантический слой убирают цепочки ручных трансформаций — отчёт собирается за минуты.
- **Безопасность и комплаенс.** Изоляция медданных, единый IAM и аудит снижают регуляторные риски по мед- и фин-данным.
